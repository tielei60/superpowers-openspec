# 方案文档到 OpenSpec 计划转换流程

## 1. 使用场景

当用户要求基于 `docs/solutions/<主题>.md` 生成 OpenSpec 计划时使用。

前提条件：

- `docs/solutions/<主题>.md` 已完成评审并得到用户确认
- 如果方案文档尚未确认，不直接进入本流程，应先回到 `references/planning-workflow.md` 完成方案确认门禁
- 本流程处理的是“已确认方案文档 -> OpenSpec 计划”的承接，不替代方案先行流程

如需在方案目录旁保留专题说明，可复用本文结构写入：

`docs/solutions/references/<主题>-OpenSpec-拆分设计.md`

如果该拆分设计已经创建，可把它作为辅助承接材料；但来源方案仍然是 `docs/solutions/<主题>.md`，不能用拆分设计替代来源方案文档。

---

## 2. 基本流程

1. 读取方案文档
2. 提取方案摘要
3. 判断是否可以生成 OpenSpec 计划
4. 生成或更新 `proposal.md` / `spec.md` / `design.md` / `tasks.md`
5. 输出对齐检查

## 4. OpenSpec 拆分设计

拆分设计是**落点索引文档**，不是内容副本。

### 职责定位

核心原则：

1. **方案文档是"内容"，拆分设计是"索引"，OpenSpec 产物是"载体"。**
2. **每个拆分都必须有清晰明确的目标。**

| 应该有 | 不应该有 |
|--------|----------|
| 来源方案文档引用 | 重复方案的设计内容 |
| 章节→artifact 映射表 | 完整章节副本 |
| change 拆分建议（单/多 change） | 详细流程/架构描述 |
| 每个拆分的清晰目标 | 取舍分析原文 |
| 依赖顺序与优先级 | 验收标准原文 |
| 边界划分理由 | 替代方案文档作为评审对象 |
| 易遗漏内容提示 | |
| 同步规则 | |

### 必备要素

1. **来源方案文档**：明确引用哪些方案，多方案时全部列出
2. **内容落点映射表**：章节→artifact 映射，避免关键内容漏落
3. **change 拆分建议**：单 change 或多 change 划分，每个拆分必须有清晰目标
4. **依赖顺序**：多 change 时的执行顺序与依赖关系
5. **优先级**：P0/P1/P2 排序，关键路径优先
6. **边界划分理由**：为什么这样拆，便于追溯
7. **易遗漏内容提示**：验收标准、兼容性、迁移、回滚等容易漏掉的关键点
8. **同步规则**：方案变化时如何更新拆分设计

### 模板

```md
# OpenSpec 拆分设计：<主题>

## 来源方案文档

- `docs/solutions/<主题>.md`

## 内容落点映射表

| 方案章节 | 落点 artifact | 说明 |
|---------|--------------|------|
| 背景、目标、非目标 | proposal.md | 直接引用，不重写 |
| 业务规则部分 | spec.md | 提取规则条目 |
| 架构设计、流程图 | design.md | 承接图示与模块边界 |
| 关键取舍 | proposal.md | 放入"为什么这样做" |
| 验收标准 | spec.md | 转为验收场景 |
| 风险与兼容性 | proposal.md + design.md | 分别承接影响范围和技术约束 |
| 待确认问题 | proposal.md | 列出未决项 |

## change 拆分建议

本方案拆分为 N 个 OpenSpec change：

| change 名称 | 目标 | 范围 | 优先级 | 依赖 |
|------------|------|------|--------|------|
| change-xxx | <清晰明确的目标> | ... | P0 | 无 |
| change-yyy | <清晰明确的目标> | ... | P1 | change-xxx |

边界划分理由：<说明为什么这样拆>

## 易遗漏内容提示

- 验收标准是否已转为可验证场景
- 兼容性影响是否已说明 fallback/回滚策略
- 迁移步骤是否已列出数据迁移、状态延续规则
- 外部依赖是否已识别上游接口、第三方约束

## 同步规则

- 方案文档实质变化 → 检查并更新拆分设计映射表
- 新增章节 → 补充落点映射
- 范围调整 → 重新评估 change 拆分建议

## 未决项处理

- 哪些问题阻塞 `tasks.md`
- 哪些问题可以先生成 `proposal.md` / `spec.md` / `design.md`
- 是否需要先进入 `/opsx:explore`
```

---

## 5. `tasks.md` 拆分要求

重点不是“把方案改写成任务列表”，而是把已经明确的实施动作拆成可执行任务。

每个任务至少包含：

- 任务名称
- 任务类型：实施 / 迁移 / 验证
- 完成判断

如果方案存在关键未决项，不要直接生成完整 `tasks.md`，应先提示需要补齐或进入 `/opsx:explore`。

---

## 6. 简单对齐检查

生成后检查：

| 检查项 | 结果 |
| --- | --- |
| 已读取来源方案 | 通过 / 不通过 |
| `proposal.md` 已写入来源方案 | 通过 / 不通过 |
| `spec.md` 已承接关键规则 | 通过 / 不通过 |
| `design.md` 已承接设计要点 | 通过 / 不通过 |
| `tasks.md` 每项有完成判断 | 通过 / 不通过 |
| 每个拆分有清晰明确的目标 | 通过 / 不通过 |
| 未决项已说明 | 通过 / 不通过 |
