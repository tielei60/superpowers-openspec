# OpenSpec 产物参考模板

本文件不再定义自定义 `openspec.md` 模板。
它只说明官方 OpenSpec / OPSX 常见产物各自应该承载什么内容。

如果用户要求先确认完整方案文档，应先使用 `docs/solutions/*.md`。该方案文档不是 OpenSpec 官方 artifact，而是面向用户评审的上游方案来源。用户确认后，再进入 OpenSpec change。

`docs/solutions/*.md` 与 OpenSpec 产物的默认关系：

- `docs/solutions/*.md`：完整中文方案、背景、取舍、风险、验收口径
- `proposal.md`：引用来源方案文档，并说明为什么改、改什么、影响什么
- `design.md`：承接设计细节、模块边界、图示和技术取舍
- `spec.md`：承接行为规范、规则和场景
- `tasks.md`：承接实现计划和验证任务

## `proposal.md`

用途：

- 解释为什么要改
- 解释改什么
- 解释影响范围

建议至少包含：

1. 背景
2. 目标
3. 变更范围
4. 影响面
5. 风险或注意事项

如果该 change 来源于已确认方案文档，`proposal.md` 应靠前包含：

```md
## 来源方案文档

本变更基于以下已确认方案文档生成：

- `docs/solutions/<主题>.md`
```

为减少返工，`proposal.md` 还建议明确：

- 非目标：这次不解决什么
- 关键假设：当前方案成立依赖哪些前提
- 外部依赖：第三方、上游系统、外部接口或组织流程约束
- 待确认项：哪些信息缺失会影响后续设计或开发

## `spec.md`

用途：

- 描述能力的行为要求与场景
- 作为规范层的核心事实表达

建议重点关注：

1. Requirement
2. Scenario
3. 输入条件
4. 触发行为
5. 预期结果
6. 边界与异常

为减少返工，`spec.md` 还建议明确：

- 兼容性要求：旧接口、旧行为、旧状态是否继续兼容
- 状态与约束：哪些规则不能被实现阶段随意更改
- 验收标准：怎样才算需求完成，如何验证
- 未决边界：哪些场景仍需进一步澄清

## `design.md`

用途：

- 描述实现思路、边界、模块关系和设计取舍

适合放在这里的内容：

- 架构说明
- 数据流
- 时序说明
- 关键设计权衡
- Mermaid 图或其他设计补充
- 错误处理、降级与失败路径
- 迁移、回滚、兼容性处理
- 监控、审计或验证补充

### 图示补充原则

当仅靠段落文字不足以完整表达方案时，应在 `design.md` 中补充图示。常见判断标准：

- 模块较多，关系和依赖方向容易混淆
- 流程较长，存在分支、回退、异常或状态流转
- 涉及前后端、服务间调用、事件通知或异步时序
- 涉及列表页、详情页、表单页、弹窗或信息区块布局

默认优先级：

1. Mermaid
2. ASCII

建议用法：

- 架构关系、模块边界、数据流：优先 Mermaid
- 流程、状态、审批路径：优先 Mermaid `flowchart` / `stateDiagram`
- 调用链路、角色协作、异步交互：优先 Mermaid `sequenceDiagram`
- 页面结构、表单布局、列表区域说明：优先 ASCII 文本布局图

使用原则：

- 图示应作为 `design.md` 或相关设计说明的一部分
- 如果输出 Mermaid 图，最后应做一次自检，确认图类型、节点/参与者标识、括号与连线、代码块 fence 等没有明显语法错误
- 不要把 `architecture.mermaid`、`flowchart.mermaid`、`sequence.mermaid` 重新定义为官方强制独立文件
- 不要在复杂结构明明需要图示时只保留纯文字说明

为减少返工，`design.md` 还建议补足：

- 关键设计假设是否成立
- 哪些依赖必须先就绪
- 是否涉及历史数据迁移、状态修复或兼容层
- 出错时如何降级、回滚或兜底
- 哪些验证点需要在实现前后重点检查

## `tasks.md`

用途：

- 把变更拆成可执行的实现清单

建议重点关注：

1. 任务拆分是否清晰
2. 顺序是否合理
3. 是否能支撑实现与验证

为减少返工，`tasks.md` 还建议明确：

- 前置依赖和阻塞项
- 迁移、兼容层、回滚预案是否需要单独成任务
- 验证与验收任务是否显式存在
- 哪些任务必须串行，哪些任务可以并行

## 减少返工的统一检查维度

无论是 `proposal.md`、`spec.md`、`design.md` 还是 `tasks.md`，都可以用下面五类问题做快速自检：

1. 假设是否已经写明，而不是藏在脑中
2. 待确认问题是否被列出来，而不是带着不确定性直接开工
3. 依赖与约束是否已经识别
4. 兼容性、迁移、回滚是否已经考虑
5. 验收与验证方式是否可以落地执行

## 可选补充产物

以下内容不是 OpenSpec 官方强制 artifact，但在用户明确要求保留原始输入时可以补充：

### `source-notes.md`

用途：

- 记录用户原始输入摘录
- 记录会议纪要片段
- 记录需求来源、背景材料和关键决策依据

适合放在这里的内容：

- 原始需求原文片段
- 已确认的事实来源
- 讨论中明确拍板的约束

### `transcript.md`

用途：

- 记录更完整的对话或沟通过程

适合放在这里的内容：

- 多轮对话原文
- 需求澄清过程
- 会议讨论纪要全文

使用原则：

- 仅在用户明确要求保留原始输入时添加
- 放在 `openspec/changes/<change-name>/` 下
- 不替代 `proposal.md`、`spec.md`、`design.md`、`tasks.md`

## 文档可读性原则

`docs/solutions/*.md`、`proposal.md`、`spec.md`、`design.md` 和 `tasks.md` 都应使用人类易读语义。

- 避免 AI 式套话和生硬堆叠
- 术语首次出现需解释
- 优先短句，先说结论
- 对比、枚举、角色权限、状态映射优先用表格
- 避免内部缩写和未解释代号
- 技术细节应说明其实际含义

## 使用本文件时的原则

- 不要再把 OpenSpec 理解成单个 `openspec.md`
- 不要再把 Mermaid 三图写成固定强制目录要求
- 以官方 `proposal.md`、`spec.md`、`design.md`、`tasks.md` 语义为准
- 如果先生成了 `docs/solutions/*.md`，必须先确认方案文档，再创建或更新 OpenSpec change
- 如果 OpenSpec 产物实质变化，必须检查是否需要同步回 `docs/solutions/*.md`
- 原始输入记录属于可选补充，不属于官方默认 artifact
