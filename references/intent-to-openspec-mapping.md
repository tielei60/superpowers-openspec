# 中文意图到 OpenSpec 的命令映射

本文件说明：当用户在 `superpowers` 体系里使用中文表达"需求沟通、方案、计划、规范、功能改造、功能优化、实现"时，`superpowers-openspec` 应如何把这些意图稳定组织成面向 OpenSpec 的方案、规范与计划工作流。

目标不是重新发明一套命令，而是减少上层 `superpowers` 把本应进入规范阶段的请求过早吞掉。

## 核心原则

- `superpowers` 负责识别是否需要进入规范阶段
- `superpowers-openspec` 负责把中文意图组织成面向 OpenSpec 的方案、规范与计划工作流
- 只要本轮核心诉求是"方案、计划、规范、需求沟通、功能改造、功能优化"，且会影响规则、流程、接口、状态、数据结构或模块边界，就不应因为句子里出现"实现"而直接进入编码
- 除非用户明确要求其他语言，否则生成的 `docs/solutions/*.md`、`proposal.md`、`spec.md`、`design.md`、`tasks.md` 内容本身也应使用中文

## 常见中文意图映射

| 中文意图 | 典型说法 | OpenSpec 含义 | 主要产物/重点 | 推荐入口 |
| --- | --- | --- | --- | --- |
| 需求沟通 / 先分析 / 先梳理 | `先沟通需求` `先分析一下` `先帮我梳理` | 先收敛问题空间 | 假设、待确认问题、依赖、边界 | `/opsx:explore` |
| 完整方案文档先行 | `先写完整 markdown 方案` `确认方案文档后再生成 OpenSpec` | 先形成便于用户评审的方案来源 | `docs/solutions/*.md`，确认后再生成 OpenSpec change | 先写方案文档，确认后再进入 `/opsx:*` |
| 先写方案 / 先定方案 | `先把方案定下来` `先写方案` | 说明为什么做、做什么、怎么设计 | `proposal.md` + `design.md` | `/opsx:propose` 或 `/opsx:ff` |
| 先写计划 / 开发计划 | `先写计划` `先把开发计划定下来` | 形成执行拆解 | `tasks.md` | 若前置未定，先 `/opsx:explore` 或 `/opsx:new` + `/opsx:continue` |
| 先定规范 / 规则 / 行为 | `先把规则写清楚` `先定规范` | 明确行为约束与场景定义 | `spec.md` | `/opsx:propose` |
| 功能改造 / 功能优化 / 能力升级 | `优化这个功能` `改造现有流程` `升级这个模块能力` | 若影响规则、流程、接口、状态、数据结构或模块边界，应先规划 | 方案、规范、计划是否都需要更新 | `/opsx:explore` 或 `/opsx:propose` |
| 方案 + 计划一起做 | `先把方案和开发计划定下来` | 先规划，再拆执行 | `proposal.md` + `design.md` + `tasks.md` | `/opsx:new` + `/opsx:continue` 或 `/opsx:ff` |
| 设计并实现 / 规划并落地 | `帮我设计并实现短信发送功能` | 带实现诉求的规范入口 | 先确定 proposal/spec/design/tasks，再实现 | 先 `/opsx:propose` 或 `/opsx:explore`，不要直接编码 |
| 直接全出 | `proposal、spec、design、tasks 一次生成` | 一次性生成完整规划产物 | `proposal.md` `spec.md` `design.md` `tasks.md` | `/opsx:ff` |
| 开始实现 | `按 tasks 开始做` `进入实现阶段` | 规范阶段已完成 | 消费现有规划产物进入实现 | `/opsx:apply` |
| 归档 | `这次变更做完了，归档` | 变更结束，不再活跃 | 归档当前 change | `/opsx:archive` |

## 路由优先级

当用户同时表达"规范意图"和"实现意图"时，按以下顺序判断：

1. 先判断是否涉及新功能、功能改造、功能优化、规则、接口、交互、数据结构、状态、模块边界或角色变化
2. 如果是，再判断本轮是否出现 `方案`、`计划`、`规范`、`需求沟通` 这些关键词或等价表达
3. 只要出现，就优先路由到 `superpowers-openspec`
4. 在 OpenSpec 产物明确前，不进入直接实现建议

## 详细场景示例

### 1. 先探索，再决定怎么规范

用户表达：

- `先分析一下再开发`
- `我这边需求还比较乱，先帮我理一下`
- `先把问题空间摸清楚`

推荐处理：

- 优先进入 `/opsx:explore`
- 形成较稳定方向后，再进入 `/opsx:propose`

### 2. 需求已经比较完整，直接进入规划

用户表达：

- `先写 spec`
- `先做详细设计`
- `需求已经确定，直接按 OpenSpec 走`

推荐处理：

- 优先进入 `/opsx:propose`

### 2A. 用户把设计、方案或计划和实现混在同一句里

用户表达：

- `帮我设计并实现短信发送功能`
- `先把方案和开发计划定下来，再落地`
- `先沟通需求，然后把这个功能做出来`

推荐处理：

- 不要因为出现了"实现"就直接跳过规范阶段
- 若需求边界已经比较清晰，优先进入 `/opsx:propose`
- 若输入仍然零散、假设较多或依赖未定，优先进入 `/opsx:explore`

说明原则：

- 这类表达本质上是"带实现诉求的规范入口"
- 只要任务属于新功能、规则、接口、交互、数据结构、状态或角色变化，就应先由 `superpowers-openspec` 接管
- 在 `proposal.md`、`spec.md`、`design.md`、`tasks.md` 确认前，不应直接进入实现建议

### 2B. 用户提出功能改造、功能优化、流程优化或能力升级

用户表达：

- `优化现有审批功能`
- `改造这个流程`
- `升级这个模块能力`
- `重构这个模块边界`

推荐处理：

- 如果会影响规则、流程、接口、状态、数据结构、角色行为或模块边界，进入面向 OpenSpec 的方案、规范与计划工作流
- 若边界清晰，优先进入 `/opsx:propose`
- 若影响范围、兼容策略或验收口径未定，优先进入 `/opsx:explore`

不推荐处理：

- 不要因为用户只说"优化"就直接进入编码
- 也不要把所有局部性能优化都强制拉进 OpenSpec；如果不改接口、规则、状态、数据结构或模块边界，可以按普通任务处理

### 3. 输入是会议纪要、聊天记录、口语描述

用户表达：

- `这是会议纪要，你先整理需求`
- `下面是零散讨论，先沉淀规范`
- `先从这些聊天记录里提炼规则`

推荐处理：

- 优先进入 `/opsx:explore`
- 或明确说明需要先收敛，再进入 `/opsx:propose`

### 4. 用户希望按步骤生成 proposal / spec / design / tasks

用户表达：

- `我想一步一步来`
- `先建 change，再逐步补 proposal 和 design`
- `不要一次全出，按阶段推进`

推荐处理：

- 使用 `/opsx:new`
- 然后使用 `/opsx:continue`
- 若用户想一次补齐，也可改为 `/opsx:ff`

### 5. 用户希望一次把规划产物生成完

用户表达：

- `直接把 proposal、spec、design、tasks 一次搞出来`
- `我不需要分步看，先生成完整规划产物`

推荐处理：

- 使用 `/opsx:ff`

### 6. 用户已经确认规划，准备进入实现

用户表达：

- `规划好了，开始做`
- `按 tasks 开始实现`
- `进入实现阶段`

推荐处理：

- 使用 `/opsx:apply`

### 7. 用户要校验实现是否符合规范

用户表达：

- `检查实现有没有偏离 spec`
- `验证这次改动是否和规划一致`

推荐处理：

- 在 profile 支持时使用 `/opsx:verify`

### 8. 用户要把变更规范同步回主规范

用户表达：

- `把这次变更 spec 合回主规范`
- `同步 changes 里的规范到主 specs`

推荐处理：

- 在 profile 支持时使用 `/opsx:sync`

### 9. 用户希望保留原始输入或对话过程

用户表达：

- `把我原始需求也记录下来`
- `保留这次会议纪要原文`
- `把对话过程一起存档`

推荐处理：

- 正常进入对应的 `/opsx:*` 规范流程
- 同时说明可选补充文件：
  - `openspec/changes/<change-name>/source-notes.md`
  - `openspec/changes/<change-name>/transcript.md`

说明原则：

- 这两个文件是可选补充
- 不属于 OpenSpec 官方默认强制 artifact
- 只在用户明确要求保留原始输入时建议使用

### 10. 用户要求先写完整方案文档

用户表达：

- `先帮我写一个完整 markdown 方案文档，确认后再生成 OpenSpec change`
- `先把可完整评审的方案落到 docs/solutions`
- `先确认方案文档，再拆 OpenSpec 的规范和计划`

推荐处理：

- 先生成 `docs/solutions/<主题>.md`
- 方案文档必须使用中文
- 请求用户确认方案文档前，询问是否需要先做方案文档自我闭环验证
- 自我闭环验证由用户决定，不是强制步骤
- 用户确认方案文档之前，不创建或更新 OpenSpec change
- 用户确认后，再进入合适的 `/opsx:*` 流程
- `proposal.md` 必须包含"来源方案文档"章节

说明原则：

- `docs/solutions/*.md` 不是 OpenSpec 官方 artifact
- 它是便于用户评审的上游方案来源
- 不要新增 `sources.md` 或 `source-docs.md`

### 11. 用户基于多个方案文档生成一个 OpenSpec change

用户表达：

- `基于 docs/solutions/方案一.md 和 docs/solutions/方案二.md 创建 OpenSpec change`
- `把这两个方案合成一个 OpenSpec 计划`

推荐处理：

- 确认这些方案文档已经过用户确认
- 在 `proposal.md` 中列出全部来源方案文档
- 后续再生成或更新 `spec.md`、`design.md` 和 `tasks.md`

`proposal.md` 示例：

```md
## 来源方案文档

本变更基于以下已确认方案文档生成：

- `docs/solutions/方案一.md`
- `docs/solutions/方案二.md`
```

### 12. 用户明确表示复杂关系单靠文字讲不清，或主动要求补图

用户表达：

- `这个方案最好配个架构图`
- `流程有点复杂，最好画个流程图`
- `这里涉及多个角色和异步通知，给我一个时序图`
- `这个页面很多区块，最好给个文本布局图`

推荐处理：

- 正常进入对应的 `/opsx:*` 规范流程
- 同时明确说明：后续 OpenSpec 产物中应补充图示，而不是只保留纯文字
- 默认优先 Mermaid；如果目标是页面文本布局，或当前载体更适合纯文本快速审阅，则使用 ASCII

补充建议：

- 模块边界、依赖方向、数据流向：Mermaid 架构图
- 业务分支、状态推进、审批回路：Mermaid 流程图 / 状态图
- 多角色、多系统、异步交互：Mermaid 时序图
- 列表页、详情页、表单页、弹窗：ASCII 文本布局图

说明原则：

- 图示是 `design.md` 或相关设计说明里的表达方式
- 如果输出 Mermaid 图，最后要做一次自检，确认没有明显语法错误再交付
- 不是本 skill 新定义的独立官方 artifact
- 不要把 Mermaid 三图重新写成固定强制独立文件

### 13. 需求方向基本明确，但假设、依赖、迁移或验收口径还没定

用户表达：

- `功能方向没问题，但第三方回调字段还没确认`
- `页面流程差不多了，不过历史数据怎么迁移还没定`
- `方案基本能做，但接口兼容和验收方式还没统一`
- `先给我任务清单，细节后面开发时再补`

推荐处理：

- 不要直接假装"已经完整，可以无风险进入开发"
- 优先进入 `/opsx:explore` 收敛未决项
- 或使用 `/opsx:new` + `/opsx:continue` 分步补齐 proposal / spec / design / tasks

输出应额外指出：

- 哪些是假设
- 哪些仍待确认
- 哪些依赖或外部约束尚未锁定
- 是否存在兼容性、迁移、回滚或验收风险

说明原则：

- 这些内容的目标是减少开发返工
- 它们不是阻止推进，而是避免带着隐性不确定性直接进入实现
- 如果未决项足以改变实现方案，不应直接把 `tasks.md` 当作已可执行清单

## 文档可读性要求

文档应使用人类易读语义，避免 AI 式套话。

- 术语首次出现需解释
- 优先短句，先说结论
- 对比、枚举、状态映射优先用表格
- 避免内部缩写和未解释代号

## 典型反例

以下做法说明路由错了：

- 用户说 `先把方案和开发计划定下来`，却直接返回编码步骤
- 用户说 `帮我设计并实现...`，却因为含有 `实现` 就跳过规范阶段
- 用户说 `优化这个功能` 或 `改造这个流程`，且影响规则/接口/状态，却直接进入编码
- 用户说 `先写规范`，却只给通用需求摘要，没有映射到 OpenSpec 命令与产物
- 把用户直接导向 `docs/specs/<feature>/openspec.md`
- 把 Mermaid 三图当作固定强制输出
- 明明需要图示却只给纯文字说明
- 假设、依赖、迁移或验收口径未定时，仍然直接给出"完整可执行任务清单"
- 在规范阶段还没完成前就直接进入实现建议
- 用户要求完整方案文档时，跳过 `docs/solutions/*.md` 直接创建 OpenSpec change
- 新增 `sources.md` 或 `source-docs.md` 记录来源关系，而不是写入 `proposal.md`

## 推荐对外话术

- `当前请求虽然包含"实现"，但本轮核心诉求仍然是先定方案/计划，因此应先进入 OpenSpec 规范阶段。`
- `你说的"完整方案文档"默认对应 docs/solutions/*.md；"方案"默认对应 proposal.md 和 design.md；"计划"默认对应 tasks.md；"规范"默认对应 spec.md。`
- `如果关键信息还不完整，我会先建议 /opsx:explore，而不是直接开始实现。`
